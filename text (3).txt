PROJECT: HARDWARE-ASSISTED FILE INTEGRITY MONITORING (HA-FIM)

1. YOUR ROLE

Act as a senior cybersecurity systems architect, systems programmer, cloud security engineer, full-stack developer, and software testing engineer.

Your task is to design, implement, test, document, and prepare for deployment a functional Hardware-Assisted File Integrity Monitoring system called HA-FIM. Build the design to be clean simple and professional 

The system is based on the research proposal:

“Hardware-Assisted File Integrity Monitoring Using Trusted Execution Environments (TEEs) in Cloud Infrastructure.”

This is a cybersecurity research prototype intended for academic research, experimental evaluation, and demonstration.

Do not merely generate a frontend, a project proposal, mock dashboards, or static screenshots. Build an operational application with working backend services, file integrity monitoring, cryptographic hashing, baseline protection, event detection, alerting, testing, and a genuine Trusted Execution Environment integration path.

Where hardware-backed functionality cannot be executed in the current environment, implement the software components that can run locally and clearly separate them from the real hardware-backed components.

Never claim that a security feature is hardware-protected unless that protection has actually been implemented and verified.

2. PRIMARY OBJECTIVE

Build a system that detects unauthorized changes to files and directories while protecting its security-critical monitoring logic and trusted file baseline from attacks targeting the operating system or hypervisor.

Traditional File Integrity Monitoring systems generally depend on the host operating system. An attacker who compromises the operating system may be able to modify files, alter the trusted baseline, disable the monitoring agent, or suppress alerts.

HA-FIM must address this limitation by placing the security-critical comparison engine and protected baseline state inside a supported Trusted Execution Environment.

The system must monitor designated files and directories for:

	•	File creation.
	•	File modification.
	•	File deletion.
	•	File permission changes.
	•	Changes to relevant file metadata.
	•	Changes to file contents.
	•	Attempts to interfere with the host-side monitoring component.
	•	Attempts to alter or suppress reported integrity violations.

Use SHA-256 as the primary file-content hashing algorithm.

3. TECHNICAL ACCURACY REQUIREMENTS

Before implementing the TEE integration, investigate the actual hardware and software requirements of the target environment.

Important distinctions:

	•	Intel SGX provides application-level enclave isolation on supported platforms.
	•	AMD SEV-family technologies protect virtual machines using hardware-assisted memory encryption and related isolation mechanisms.
	•	ARM TrustZone separates execution into Normal and Secure worlds on supported ARM platforms.
	•	AWS Nitro Enclaves provide isolated compute environments using the AWS Nitro architecture. They are not Intel SGX enclaves.
	•	Azure Confidential Computing and Google Cloud Confidential VMs must be evaluated according to their actual supported confidential-computing technologies and instance configurations.

Do not assume these technologies provide identical security guarantees.

For the primary implementation, investigate AWS Nitro Enclaves as the target environment, consistent with the research proposal’s intended cloud deployment.

Verify the current AWS Nitro Enclaves SDK, supported instance requirements, enclave communication mechanisms, attestation capabilities, and deployment prerequisites using official documentation.

If Nitro Enclaves cannot be used within the available budget or account permissions, implement an alternative supported TEE adapter where feasible.

Do not silently substitute ordinary Docker containers, software emulation, or a conventional virtual machine for a hardware-backed TEE.

Any fallback must be explicitly identified as a development or simulation mode.

5. SYSTEM ARCHITECTURE

Implement the following logical components.

Component A: Host Monitoring Agent

The host monitoring agent is responsible for:

	1.	Watching explicitly configured files and directories.
	2.	Detecting filesystem events.
	3.	Reading file content and relevant metadata.
	4.	Sending the required data to the integrity verification service.
	5.	Receiving authenticated comparison results.
	6.	Forwarding event information to the backend reporting service.
	7.	Reporting its own health status.
	8.	Detecting interruptions in its monitoring operations where feasible.

The host agent must be treated as potentially compromised.

Do not place the authoritative trusted baseline exclusively in host-accessible storage.

Do not assume that filesystem event notifications are complete or trustworthy.

Implement periodic reconciliation scans to identify changes missed by filesystem notifications.

Use stable file identifiers and metadata where appropriate to handle renames, hard links, and races between file access and modification.

Clearly document the limitations of monitoring when the host kernel is compromised.

Component B: TEE-Resident Comparison Engine

Implement the security-critical integrity verification engine inside the selected TEE.

The engine must:

	1.	Accept validated file verification requests.
	2.	Compute or verify SHA-256 hashes using trusted cryptographic code.
	3.	Maintain protected baseline records.
	4.	Compare observed file content against the expected baseline.
	5.	Identify new, modified, deleted, or permission-changed files.
	6.	Generate structured integrity results.
	7.	Maintain relevant protected state.
	8.	Reject malformed requests and invalid state transitions.
	9.	Authenticate communication with authorized host-side components.
	10.	Support baseline initialization, authorized baseline updates, and integrity verification.

The authoritative baseline must not be trusted merely because the host agent supplies it.

Design baseline initialization and updates so that only an authorized administrator can approve them.

Use authenticated administrative operations, signed requests where appropriate, and replay protection.

A baseline update must not silently approve a file modification that was never authorized.

Where feasible, use a protected monotonic sequence number or equivalent anti-replay mechanism. Clearly document any limitations if durable anti-rollback protection is unavailable.

Component C: Baseline Management

Implement a secure baseline management service.

For each monitored file, maintain relevant information such as:

	•	File identifier or normalized path.
	•	SHA-256 hash.
	•	File size.
	•	File permissions.
	•	Relevant timestamps.
	•	Baseline creation time.
	•	Baseline version.
	•	Authorized update history.
	•	Verification status.

Provide operations for:

	•	Initializing a baseline.
	•	Viewing baseline records.
	•	Comparing observed state with the baseline.
	•	Approving an authorized change.
	•	Updating the baseline through an authenticated administrative workflow.
	•	Exporting baseline information for authorized investigation.

Never provide an unauthenticated endpoint that allows arbitrary users to replace the trusted baseline.

If a baseline is lost or the TEE is restarted, the system must not silently trust a replacement supplied by the host.

Implement a documented recovery and reinitialization process.

Component D: Host-to-TEE Communication Interface

Design a narrow communication interface between the host agent and the TEE.

The interface must:

	•	Validate message structure and length.
	•	Authenticate requests where feasible.
	•	Validate response authenticity.
	•	Reject malformed messages.
	•	Use request identifiers.
	•	Prevent replay of security-sensitive operations.
	•	Handle timeouts and communication failures.
	•	Limit the information exposed outside the TEE.
	•	Avoid unnecessary disclosure of sensitive file contents.

For AWS Nitro Enclaves, use the supported communication mechanisms and SDKs rather than inventing an unsupported enclave interface.

Investigate whether the selected architecture should transmit file contents, file hashes, or a combination of content and metadata.

Explain the security consequences of the selected design.

If file content is read outside the TEE before being submitted for verification, document that the compromised host may influence what the TEE receives.

Do not claim that the TEE can independently observe the host filesystem unless the implementation actually provides such a capability.

Component E: Alerting and Reporting Service

Implement a functional alerting system.

Every integrity violation must generate a structured event containing, where available:

	•	Unique event identifier.
	•	Event timestamp.
	•	File path or identifier.
	•	Event type.
	•	Expected SHA-256 hash.
	•	Observed SHA-256 hash.
	•	Expected permissions.
	•	Observed permissions.
	•	Severity.
	•	Verification result.
	•	Monitoring agent status.
	•	TEE verification status.
	•	Relevant baseline version.
	•	Correlation or request identifier.

Do not expose sensitive file contents in the event log.

Support alert categories including:

	•	Unauthorized modification.
	•	Unexpected file creation.
	•	File deletion.
	•	Permission change.
	•	Baseline verification failure.
	•	Monitoring agent interruption.
	•	TEE communication failure.
	•	Invalid or replayed request.
	•	Unauthorized baseline update attempt.
	•	Unavailable or unverifiable TEE attestation.

Implement a persistent event log.

Support real-time updates in the dashboard.

Provide filtering by severity, event type, file, date, and verification status.

Provide CSV export for authorized users.

Do not automatically mark a security incident as resolved simply because the monitored file later returns to its original state.

6. SECURITY AND TRUST MODEL

Implement the system around an explicit threat model.

Assume an attacker may:

	•	Modify monitored files.
	•	Delete monitored files.
	•	Change file permissions.
	•	Obtain root privileges on the host.
	•	Modify the host monitoring agent.
	•	Modify ordinary host-side baseline files.
	•	Attempt to suppress alerts.
	•	Attempt to replay previously valid requests.
	•	Attempt to provide stale or manipulated filesystem observations.

The primary security objective is to protect the comparison engine and its authoritative baseline from host kernel or hypervisor interference, to the extent supported by the selected TEE architecture.

Document the limits of this protection.

In particular:

	•	A TEE cannot automatically prove that host-supplied file content is the current or genuine content of a filesystem object.
	•	A compromised host may withhold events or deny service.
	•	An attacker may exploit vulnerabilities in the TEE application itself.
	•	Attestation depends on correctly validating the evidence and the expected measurements.
	•	A compromised administrator account may authorize malicious baseline changes.
	•	Hardware-backed isolation does not automatically eliminate side-channel risks.
	•	A compromised host may interfere with alert delivery outside the TEE.
	•	A hash comparison detects differences but does not establish whether a change was authorized.

Where possible, protect alert authenticity using signed or authenticated event messages.

Design the backend to distinguish between a cryptographically verified event and an event reported by an untrusted host component.

13. IMPORTANT SECURITY DESIGN ISSUE: TRUSTED FILE CONTENT

The system must explicitly address the difficulty of verifying files on a host that may be compromised.

A TEE does not automatically have trusted access to the host filesystem.

If the host reads a file and submits its content to the TEE, a compromised host may submit stale, substituted, or fabricated content.

Implement the strongest practical design supported by the selected architecture.

At minimum:

	1.	Ensure that baseline records are protected from ordinary host modification.
	2.	Authenticate requests and responses.
	3.	Use request identifiers and replay protection.
	4.	Record verification timestamps and source information.
	5.	Detect unexpected baseline state changes.
	6.	Report when trustworthy verification cannot be established.
	7.	Explain the limitations of host-supplied content.
	8.	Investigate available remote attestation and trusted measurement mechanisms.
	9.	Avoid claiming complete protection against a malicious kernel unless the design actually establishes that property.

Document the difference between:

	•	Detecting ordinary filesystem changes.
	•	Protecting baseline integrity.
	•	Protecting the comparison engine.
	•	Establishing the authenticity of file observations.
	•	Ensuring that alerts reach an external recipient.

These are distinct security properties.
